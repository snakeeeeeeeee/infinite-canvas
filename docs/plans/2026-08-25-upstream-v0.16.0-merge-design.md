# Upstream v0.16.0 Merge Design

## Goal

Merge the official `v0.16.0` release into the fork while preserving its current SuperToken integration, provider-specific generation controls, media references, model selection, task recovery, progress display, and detailed error handling.

## Approach

Create `codex/merge-upstream-v0.16.0` from the current fork `main` and merge the annotated release tag with a merge commit. This keeps upstream ancestry explicit and makes future upstream merges use the correct shared history. Directly merging `upstream/main` is intentionally deferred because it contains 16 unreleased commits beyond `v0.16.0`; cherry-picking release features is rejected because it would discard ancestry and make later synchronization harder.

## Conflict Ownership

- Release notes and pending-test documents combine both histories and describe the fork's actual behavior. They must not claim Ark, Seedance, or reference-media support was removed when the fork retains it.
- Canvas node and project conflicts incorporate official interaction fixes while keeping fork-specific model selection, route overrides, generation progress, failure details, and task recovery.
- Video settings and generation services use the fork as the behavioral base because official `v0.16.0` removes capabilities that the fork still exposes. Compatible upstream fixes are applied selectively.
- Locale files retain all fork keys and add upstream copy required by merged UI.
- Cleanly merged official files are accepted unless a dependency audit shows that they bypass fork-specific request configuration.

## Data And Error Flow

Existing request resolution continues through the fork's channel/SuperToken services. Reference images, videos, and audio retain their current validation and upload flow. Existing asynchronous task identity, polling, local persistence, route pinning, server error code/message propagation, and retry behavior remain authoritative. Official CORS messaging is adopted only where it complements rather than replaces the shared error parser.

## Verification Boundary

The merge is audited through Git conflict status, conflict-marker searches, focused source inspection, changed-file review, and documentation consistency. Repository instructions explicitly delegate builds, syntax checks, and automated tests to the user, so none are run as part of this merge.
